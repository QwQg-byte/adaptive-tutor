# 部署与备份

## 推荐生产结构

当前推荐 Ubuntu 原生部署：Nginx 提供前端静态文件并反向代理 FastAPI，FastAPI 通过
Python 虚拟环境运行，Neo4j 作为本机服务运行。生产环境不需要长期运行 Vite，也不要求
为了部署强制引入 Docker。

- FastAPI 仅监听 `127.0.0.1:8000`；
- Neo4j 的 `7474/7687` 不直接暴露公网；
- 公网只开放 Nginx 的 `80/443`，并配置 HTTPS、认证和访问限速；
- `.env`、SSH 密钥和备份文件只保存在受限目录，不进入 Git；
- 服务使用普通系统用户运行，关闭 debug 和 reload。

详细的本机开发启动顺序见 [启动&停止.md](../启动&停止.md)。

## Neo4j 备份

备份前确认数据库处于可用状态，并把目标目录放在项目目录之外：

```bash
neo4j-admin database dump neo4j --to-path=/var/backups/knowledge-graph
```

仓库提供了可重复执行的脚本，默认停止 FastAPI 和 Neo4j，完成离线 dump、版本记录、
SHA-256 校验、权限收紧、服务恢复和过期备份清理：

```bash
sudo bash /home/ubuntu/apps/knowledge-graph/deploy/backup_neo4j.sh
```

脚本默认保留 14 天，可通过 `BACKUP_ROOT`、`RETENTION_DAYS`、`DATABASE` 等环境变量调整。
执行前应确认 SSH 会话可恢复，执行后检查 `/var/backups/knowledge-graph/<timestamp>/`，
并把至少一份备份复制到仓库之外的异机或对象存储。脚本不会把密钥或 `.env` 写入备份目录。

备份文件至少保留一份异机或对象存储副本，并限制目录权限。备份完成后记录数据库版本、
Schema 状态、数据质量报告和备份时间。不要把备份复制到仓库或聊天窗口。

恢复必须在临时数据库或临时服务器演练，确认节点/关系统计、全文索引和主要 API 通过后，
再安排生产切换。恢复演练不能直接覆盖当前业务库。

恢复演练记录至少包含：Neo4j 版本、dump 文件校验和、Schema 状态、节点/关系计数、
全文索引状态、健康检查和主要 API 回归结果。当前云机尚未完成该演练；没有 SSH、临时主机
或隔离数据库时，不应宣称备份链路已验收。

## HTTPS、认证与限速

受控 HTTP 模板 `deploy/nginx-knowledge-graph.conf` 已加入 API 每 IP 请求和连接限制，
但正式对外使用应复制 `deploy/nginx-knowledge-graph-https.conf.example`，替换真实域名、
证书路径，并用 `htpasswd` 创建受限的 Basic Auth 文件。安装后必须执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -I http://example.org/
curl -I https://example.org/
```

正式启用前还要确认云安全组只开放 SSH、HTTP、HTTPS；FastAPI 和 Neo4j 继续只监听本机。
当前云端已应用 API 限速、安全响应头和 UFW 默认拒绝策略，但没有域名/证书和认证凭据，
因此 HTTPS 与 Basic Auth 尚未启用。

## 应用配置备份

只备份不含密钥的 `.env.example`、systemd/Nginx 配置模板和部署脚本；真实 `.env` 使用受限
权限单独保存。密钥轮换后要重新执行健康检查、Schema 检查、数据质量报告和 API 回归。

## 发布前限制

外部题库实时抓取、公网启用和特定平台适配代码，必须在获得书面许可后执行。未获许可时
只使用脱敏演示数据、人工维护链接或已授权数据源。
